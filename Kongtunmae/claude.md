# CLAUDE.md

คำแนะนำสำหรับ Claude เมื่อทำงานกับโปรเจกต์นี้ — รวมทั้งบริบทโครงการเดิม และสรุปสถาปัตยกรรม/ฟีเจอร์ฉบับเต็มจาก `ARCHITECTURE.md` + `00_HANDOFF_เริ่มที่นี่.md` (อ่านสองไฟล์นั้นเป็นแหล่งข้อมูลจริงเมื่อรายละเอียดในนี้ไม่พอ)

## บริบทโครงการ

โปรเจกต์นี้เกี่ยวข้องกับ **โครงการนวัตกรรมขับเคลื่อนหมู่บ้านกองทุนแม่ของแผ่นดินจังหวัดชุมพร** ภายใต้กรมการพัฒนาชุมชน (พช.) กระทรวงมหาดไทย โดยมีเป้าหมายเพื่อสนับสนุนการดำเนินงานของหมู่บ้านกองทุนแม่ของแผ่นดินให้มีประสิทธิภาพมากขึ้นผ่านการนำเทคโนโลยีเข้ามาช่วย

| | |
|---|---|
| ชื่อระบบ | **CDD Kongtunmae** (เปลี่ยนชื่อจาก "Click Chumphon 360" ตามคำสั่งล่าสุด) |
| หน่วยงาน | กรมการพัฒนาชุมชน (CDD) กระทรวงมหาดไทย |
| วัตถุประสงค์ | ศูนย์กลางบริหารจัดการ "กองทุนแม่ของแผ่นดิน" ครบวงจร — บันทึกกิจกรรม, ตรวจสุขภาพกองทุน, ให้คะแนน/จัดอันดับ, เฝ้าระวังยาเสพติด, รายงานผู้บริหาร |
| จังหวัดนำร่อง | ชุมพร (336 หมู่บ้านจริง / 8 อำเภอ) |
| หลักการออกแบบ | **National Template Ready** — ค่าเฉพาะจังหวัดทั้งหมดอยู่ใน `PROVINCE_CONFIG` จุดเดียว จังหวัดอื่น "Make a copy" แล้วแก้ตรงนี้ที่เดียวได้ |

**เอกสารต้นทางที่ห้ามขัดแย้ง:** `00_HANDOFF_เริ่มที่นี่.md` (decision log, roadmap 8 phases, ข้อจำกัดทางเทคนิค) และ `01_CDD_Kongtunmae.xlsx` / `01_CDD_Kongtunmae_updated.xlsx` (โครงสร้างฐานข้อมูลจริง 24 ชีต)

## กลุ่มผู้ใช้งาน (Persona)

- ผู้ใช้งานหลักคือ **คณะกรรมการหมู่บ้านกองทุนแม่ของแผ่นดิน** ซึ่ง **ไม่ถนัดเทคโนโลยี** (มักเป็นผู้สูงอายุ)
- การออกแบบ UI/UX ต้องเรียบง่ายที่สุด เน้นการลดการพิมพ์ (**Zero-Typing UI**) ใช้ Dynamic Dropdown, Radio Button, HTML5 Geolocation (ดึงพิกัดอัตโนมัติ) แทนการกรอกข้อความ — ห้ามใช้ Textbox พร่ำเพรื่อ
- ข้อความในแอปต้องใช้ภาษาที่เข้าใจง่าย ไม่ใช้ศัพท์เทคนิค หลีกเลี่ยงขั้นตอนที่ซับซ้อนหรือหลายขั้นตอนเกินไป
- ทุกหน้าจอต้องมีทางออกเสมอ (ปุ่ม "กลับเมนูหลัก" / "ติดต่อแอดมิน") ห้ามปล่อยให้ผู้ใช้ติดอยู่ในหน้าจอที่ไปต่อไม่ได้ (Dead End)

## Tech Stack (บังคับ)

- **Backend:** Google Apps Script (ทำงานร่วม Frontend ผ่าน `google.script.run` แบบ Asynchronous — **ห้ามใช้ Fetch API ยิงข้ามโดเมน** เพื่อป้องกันปัญหา CORS)
- **Database:** Google Sheets (`01_CDD_Kongtunmae.xlsx` เป็นต้นแบบโครงสร้าง — ห้ามออกแบบโครงสร้างใหม่, ห้ามแก้ผังฐานข้อมูลโดยไม่แจ้งก่อน)
- **Frontend:** HTML/JS/CSS — Tailwind CSS ผ่าน CDN, FontAwesome CDN, Google Fonts Sarabun, vanilla JS
- **Auth/เชื่อมต่อผู้ใช้:** LINE LIFF SDK v2
- **Dashboard เพิ่มเติม:** html2canvas CDN (export Infographic เป็น PNG), Chart.js CDN (กราฟ), SheetJS (xlsx) CDN (ส่งออกศูนย์ข้อมูลกลาง), Leaflet CDN + OpenStreetMap tiles (แผนที่จริง)
- **กฎเหล็ก:** Single File Component — โค้ดฝั่งหน้าบ้านต้องรวมอยู่ใน `.html` ไฟล์เดียวเสมอ (ข้อจำกัดของ Google Apps Script)

## Deliverables ปัจจุบัน (ไฟล์ที่ใช้งานจริง — canonical)

| ไฟล์ | สถานะ | หน้าที่ |
|---|---|---|
| `liff-member-app.html` | ✅ Canonical | แอปมือถือฝัง LINE (LIFF) — คณะกรรมการ/สมาชิก/เจ้าหน้าที่ทุกระดับใช้งานที่นี่ |
| `dashboard-webapp.html` | ✅ Canonical | เว็บแอปผู้บริหาร — วิเคราะห์เชิงลึก, แผนที่, พิมพ์รายงาน, Infographic |
| `cdd-kongtunmae.html` | ⚠️ เลิกใช้แล้ว | ดราฟต์แรกก่อนได้ข้อมูลจริง — **ห้ามแก้ต่อจากไฟล์นี้** เก็บไว้อ้างอิงประวัติเท่านั้น |

ทั้งสองไฟล์ canonical สร้างจาก generator scripts ที่ฝังข้อมูลจริงจาก xlsx ตรงๆ:
- `build_liff.py` → สร้าง `liff-member-app.html`
- `build_dashboard.py` → สร้าง `dashboard-webapp.html`
- ข้อมูลดิบอยู่ใน `villages.json, atypes.json, agencies.json, indicators.json, config.json, mom_quest_steps.json` (extract จาก xlsx ด้วย `extract.py` + `gen_dashboard.py`)

**เวิร์กโฟลว์เวลาแก้ฟีเจอร์:** แก้ที่ `build_*.py` เท่านั้น (ห้ามแก้ html output ตรงๆ — จะหลุดจาก source of truth) → รัน python เพื่อ regenerate → validate ก่อนส่งมอบเสมอ: JS syntax (`node --check`), duplicate `id`, onclick↔function cross-check, getElementById↔DOM id cross-check, ไม่มี placeholder token `__..._JSON__` หลงเหลือ

## RBAC — 7 ระดับสิทธิ์

| Role | ขอบเขต | บันทึกกิจกรรมได้? | อยู่ใน System_Config จริงหรือไม่ |
|---|---|---|---|
| `MEMBER` | หมู่บ้านตนเอง | ❌ อ่านอย่างเดียว | ❌ เสนอเพิ่มใหม่ — รอยืนยัน |
| `COMMITTEE` | หมู่บ้านตนเอง | ✅ | ✅ มีจริง |
| `STAFF` (พัฒนากร) | อำเภอตนเอง | ❌ | ✅ มีจริง |
| `DISTRICT_HEAD` (พัฒนาการอำเภอ) | อำเภอตนเอง | ❌ | ✅ มีจริง |
| `PROVINCE_MGR` (ผอ.กลุ่มงานส่งเสริมฯ/เจ้าหน้าที่จังหวัด) | ทั้งจังหวัด | ❌ | ✅ มีจริง — สิทธิ์จัดการ Village_Awards เฉพาะ role นี้เท่านั้น |
| `PROVINCE_HEAD` (พัฒนาการจังหวัด) | ทั้งจังหวัด | ❌ | ✅ มีจริง |
| `GOVERNOR` (ผู้ว่าราชการจังหวัด) | ทั้งจังหวัด, Read-only เข้มงวด (ปิดปุ่มซิงก์ข้อมูล) | ❌ | ❌ เสนอเพิ่มใหม่ — รอยืนยัน |

**กลไกกำหนดสิทธิ์ (Whitelist auto-assign — ตัดสินใจแล้ว ไม่ใช่ approval-queue):**
- Self-signup (LIFF) เปิดให้เลือกเองได้เฉพาะ `COMMITTEE`/`MEMBER` เท่านั้น
- ระดับ `STAFF` ขึ้นไป: ตรวจเบอร์โทรกับ `STAFF_WHITELIST` อัตโนมัติ — **ห้ามให้เลือกเอง** ของจริงต้องดึงจากชีต `Users` แทน whitelist ฝังโค้ด

**ก่อน deploy จริง:** ต้องเพิ่ม `MEMBER,GOVERNOR` เข้า `System_Config.RoleList` (ปัจจุบันมีแค่ 5 ค่า)

**ข่าวยาเสพติด — pipeline (semi-auto, ยืนยันคนเสมอ):** Ingest (RSS — ยังไม่ต่อจริง) → Suggest (จับคู่ข้อความกับ Village_Master จริง + % ความมั่นใจ) → Confirm (เจ้าหน้าที่ต้องกดยืนยันเอง **ห้าม auto-publish**) — ⚠️ หลักการสำคัญห้ามผ่อนปรน: ข้อมูลตัวอย่างต้องไม่มีรายการยืนยันแล้วมาล่วงหน้า และหัวข้อข่าวตัวอย่างต้องเป็นกลางเสมอ

**ส่งออกรูปแบบศูนย์ข้อมูลกลาง (`exportCentralFormat()`):** สร้างไฟล์ .xlsx ตรง 94 คอลัมน์จริงของระบบศูนย์ข้อมูลกลาง พช. — รหัสหมู่บ้านมาตรฐานจริงมี **11 หลัก** (จังหวัด2+อำเภอ2+ตำบล2+หมู่ที่3+suffix2) ไม่ใช่ 8 หลักที่ต้นแบบนี้เคยใช้เอง — ยังไม่ใช่การเชื่อมต่อ API จริง (`submitToCentralAPI()` มี placeholder รอ endpoint จริง)

## หลักการออกแบบ 4 ข้อ (Core Philosophy — ยึดเสมอ)

- **Zero-Typing UI** — ลดการพิมพ์ให้เป็นศูนย์ ใช้ Dropdown/Radio/GPS แทน Textbox
- **Domino Effect Automation** — Submit แล้วคืน Response ทันที งานหนัก (คำนวณ KPI, Gen PDF, e-Certificate) ใช้ Async/Time-driven Trigger รับช่วงต่อ
- **Ghost Mode Data** — แจ้งเบาะแสนิรนาม ต้องทำลายตัวตนตั้งแต่ฝั่ง Frontend ห้ามส่ง userId กลับเซิร์ฟเวอร์เด็ดขาด
- **Dynamic Printable Report** — รายงานพิมพ์ A4 ได้ (CSS `@media print`, `page-break-inside: avoid`) รองรับ 4 ระดับ จังหวัด>อำเภอ>ตำบล>หมู่บ้าน
- **National Template Ready** — ห้าม Hardcode คำว่า "ชุมพร" ในตรรกะ/UI ใช้ `Config.gs` เก็บ `PROVINCE_NAME`, `LIFF_ID`, `ADMIN_LINE_TOKEN` แยกต่างหากเสมอ

## กฎการทำงานร่วมกัน (Guardrails — สำคัญที่สุด)

- **ถามก่อนลงมือทำเสมอ** เมื่อไม่ชัดเจนหรือกระทบโครงสร้างข้อมูลที่ยืนยันแล้ว
- **ห้ามข้ามเฟส** — ทำงานทีละระยะตาม Roadmap เท่านั้น
- **ห้ามแก้ฐานข้อมูล** ในไฟล์ 01 โดยไม่แจ้งก่อน
- **เสนอทางแก้แทนการแก้เงียบ** เมื่อพบปัญหาการออกแบบเดิม
- **Single File Component** เสมอ (ดู Tech Stack)
- **Anti-Spam** — ทุกฟังก์ชันคำนวณ/บันทึกต้องเผื่อ Rate Limit ต่อวัน/สัปดาห์
- **Graceful Error Handling** — Try/Catch ทุกจุดสื่อสาร Frontend↔Backend พร้อมข้อความไทยสุภาพเข้าใจง่าย
- **UI/UX ต้องมีทางออกเสมอ** ไม่มี Dead End
- **ห้าม Hardcode ค่าเฉพาะจังหวัด** — อ้างอิงจาก `Config.gs` เท่านั้น

## หลักเมื่อเพิ่มฟีเจอร์ใหม่ต่อจากนี้

1. ห้าม hardcode ชื่อจังหวัด — ใช้ `PROVINCE_CONFIG` เสมอ
2. ทุกตัวเลข mock ต้อง deterministic (seed ผูกกับ ID) ห้ามสุ่มใหม่ทุกครั้งที่ render
3. ทุกจุดที่เป็นข้อมูลสมมติต้องมีคอมเมนต์ `TODO` หรือข้อความในหน้าจอบอกผู้ใช้ตรงๆ ว่ายังไม่ใช่ข้อมูลจริง
4. กติกาที่ไม่มีใน Handoff/xlsx ต้อง flag ว่าเป็นข้อเสนอ ไม่ใช่ข้อสรุป
5. แก้ที่ `build_*.py` เท่านั้นแล้ว regenerate — ห้ามแก้ html output ตรงๆ
6. Validate ทุกครั้งก่อนส่งมอบ (ดูหัวข้อเวิร์กโฟลว์ด้านบน)

## Decision Log สำคัญ

- **สูตรคะแนนกิจกรรม:** `TotalScore = (คะแนน + InnovationPoint) x Weight + BonusPoint` — ค่าที่ใช้ต้องแช่แข็ง ณ วันบันทึก ห้ามคำนวณใหม่ย้อนหลัง
- **คอลัมน์ Label ล้วน** (หมวดกิจกรรม, ประเภทกิจกรรม, KPI, SDG, จังหวัด/อำเภอ/ตำบล) — ให้ Apps Script Lookup จาก TypeID/VillageID เสมอ ห้ามจัดเก็บซ้ำในตารางธุรกรรม
- **ตัวชี้วัดตรวจสุขภาพ 19 ข้อ:** อัตโนมัติ 10 + กรอกมือ 9 ห้ามรวมเป็นฟอร์มเดียว
- **รอบคำนวณ:** นับกิจกรรมของ "ปีปฏิทินก่อนหน้า" เสมอ
- **Household_Members เป็นชีตทางเลือก** ห้ามบังคับกรอกครบก่อนใช้งานระบบหลัก
- **Anti-spam ปัจจุบัน:** ห้ามหมู่บ้านเดียวกันส่งกิจกรรมประเภทเดียวกันซ้ำในวันเดียวกัน (ยังไม่กันสลับประเภทบันทึกถี่ๆ — ดู Risk ด้านล่าง)
- **เกณฑ์ตัดเกรดสุขภาพกองทุน:** A ≥80% / B 50-79% / C <50%
- **Model Village Candidates:** ขั้นตอน 2 ชั้น RBAC — `DISTRICT_HEAD` เสนอชื่อเท่านั้น → `PROVINCE_HEAD` ประกาศยืนยันเท่านั้น

## สถานะจริงตอนนี้ — Data Pipeline ยังไม่เชื่อมกัน

- กดบันทึกใน LIFF → ขึ้นข้อความสำเร็จ แต่**ไม่ได้เขียนลงชีตไหนเลย** (demo state ใน browser หายเมื่อรีเฟรช)
- ปุ่มส่งออกศูนย์ข้อมูลกลางใน Dashboard → ดึงจากตัวเลข mock ไม่ได้ดึงจากแถวจริง
- **สิ่งที่ต้องทำให้เชื่อมจริง:** สร้าง Apps Script Web App รับ POST จากฟอร์ม LIFF แต่ละหน้า เขียนแถวจริงตาม data flow (Activity Entry→`Activities`+`Activity_Media`+`Activity_Network_Partners`, Health Check→`Health_Check_Form`+`Fund_Signatories`, Action Plan→`Health_Check_Action_Plan`, Ghost Mode→`AnonymousReports`) แล้วแก้ `exportCentralFormat()` ให้ดึงจากชีตจริงผ่าน API แทน mock

## การป้องกันการปั่นคะแนน (Score Gaming) — Feature ข้อ 4

**ช่องทางปั่นคะแนนที่เป็นไปได้:** บันทึกกิจกรรมไม่จริง (ช่องโหว่ใหญ่ที่สุด — ไม่มีใครตรวจก่อนเลย), เอารูปเก่ามาแนบซ้ำ, เลือกบันทึกเฉพาะประเภท weight สูง, บันทึกรัวๆ ก่อนวันประเมิน, ผ่านด่าน MOM Quest แบบนับจำนวนอย่างเดียวไม่เช็คเนื้อหา, สมยอมกันในพื้นที่

**กันไว้แล้ว:** สูตรคะแนนตายตัวจาก Activities_Type จริง, Model Village ต้องผ่านหลายเงื่อนไขร่วมกัน, GPS แนบอัตโนมัติ, ห้ามหมู่บ้านเดียวกันบันทึกประเภทเดียวกันซ้ำวันเดียวกัน

**ข้อเสนอที่ยังไม่ได้สร้าง (ต้องยืนยันก่อนทำ):**
1. **สุ่มตรวจสอบ (Spot-check)** — พัฒนากร/พัฒนาการอำเภอสุ่มยืนยัน/ปฏิเสธกิจกรรมบางส่วน
2. **Flag ความผิดปกติ** (แจ้งเตือนอย่างเดียว ไม่ตัดสิทธิ์อัตโนมัติ) เช่น บันทึกถี่ผิดปกติ, ใช้รูปซ้ำ
3. **จำกัดจำนวนกิจกรรมสูงสุดต่อวันต่อหมู่บ้าน** ให้เข้มกว่าเดิม

⚠️ ข้อสังเกต: การบันทึกกิจกรรมปัจจุบันไม่สอดคล้องกับหลัก "ระบบเสนอ มนุษย์ยืนยัน" ที่ยึดทั่วระบบ (ต่างจากข่าวยาเสพติด/หมู่บ้านต้นแบบที่มี human-confirm) — เป็นจุดเดียวที่นับคะแนนทันทีไม่มีขั้นตอนตรวจสอบ

- ออกแบบทุกหน้าจอโดยคำนึงถึงผู้ใช้งานที่ไม่ถนัดเทคโนโลยีเป็นอันดับแรกเสมอ
- ยึดตามระเบียบและขั้นตอนของกองทุนแม่ของแผ่นดินเมื่อมีเอกสารอ้างอิงชัดเจน
- เมื่อพัฒนาฟีเจอร์ใหม่ ให้ตรวจสอบว่าสอดคล้องกับ RBAC (7 ระดับ) และมาตรการป้องกันการปั่นคะแนนที่มีอยู่แล้วเสมอ
- ห้ามข้ามเฟสใน Roadmap, ห้าม hardcode ค่าจังหวัด, ห้ามแก้ฐานข้อมูลโดยไม่แจ้งก่อน — ดูหัวข้อ Guardrails ด้านบนแบบเต็ม
